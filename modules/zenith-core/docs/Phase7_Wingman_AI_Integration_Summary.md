# Phase 7: Wingman AI Integration - Implementation Summary

**Date:** 2025-11-14
**Status:** ✅ Complete

---

## Overview

Phase 7 transforms Wingman from a manual JSON command console into an AI-powered assistant. Users can now type natural language requests that are sent to an AI bridge server, which translates them into CommandAPI command sequences. The system includes a safe confirmation workflow (yes/no) before executing AI-generated commands.

---

## Components Implemented

### 1. AIBridgeClient

**Location:** `Source/network/AIBridgeClient.{h,cpp}`

**Responsibilities:**
- Send natural language + session graph to AI bridge server via HTTP POST
- Receive AI-generated command sequences with explanations
- Queue responses for UI consumption on message thread
- Notify listeners when responses arrive (ChangeBroadcaster)

**Architecture:**
- Background thread for network I/O (RT-safe, non-blocking)
- Thread-safe response queue with CriticalSection
- HTTP POST to `http://localhost:8765/wingman` (configurable)
- Uses JUCE URL::createInputStream for HTTP requests
- Retry logic: None (single attempt, fail fast)

**Key Methods:**
- `sendRequest(naturalLanguage, sessionGraph, sourceTag)` - Queue AI request
- `hasPendingResponse()` - Check for queued responses
- `popNextResponse()` - Retrieve next response
- `isConnected()` - Simple connectivity check
- `getStatusMessage()` - Debug info

### 2. WingmanPanel Extensions

**Location:** `Source/ui/WingmanPanel.{h,cpp}`

**New Features:**
- **Mode Toggle:** Command | AI buttons (radio group)
- **AI Mode:** Natural language input → AI bridge server
- **Confirmation Workflow:** yes/no before executing AI batches
- **Pending Batch State:** Holds commands until user confirms

**UI Changes:**
- Mode toggle buttons (80px each, left side of top row)
- Updated placeholder text based on mode
- Mode switch notifications in history
- AI response display with thought process
- Command list preview before execution

**Workflow:**
1. User switches to AI mode
2. Types natural language (e.g., "make a 4 bar drum loop")
3. System sends: `{text, sessionGraph}` to AI server
4. AI responds with: `{thought, commands[]}`
5. System displays plan and proposed commands
6. User types `yes` to execute or `no` to cancel
7. On `yes`: Execute batch via `CommandAPI::executeBatch()`
8. On `no`: Discard commands

**Implementation Details:**
- `Mode` enum: `Command`, `AI`
- `setMode()` - Switch modes, cancel pending batches
- `executeAIRequest()` - Send to AI bridge
- `changeListenerCallback()` - Receive AI responses
- `handleAIResponse()` - Parse and display
- `showAIPlan()` - Display thought + commands
- `executePendingBatch()` - Call CommandAPI batch execution
- `cancelPendingBatch()` - Discard commands

### 3. CommandAPI Batch Execution

**Location:** `Source/commands/CommandAPI.{h,cpp}`

**New Method:**
```cpp
juce::var executeBatch(const juce::Array<juce::var>& commands,
                       const juce::String& batchName = "Wingman AI batch");
```

**Behaviour:**
- Begins single undo transaction with `batchName`
- Executes commands sequentially
- Stops on first error (no partial rollback in v1)
- Returns aggregate result with success count and error info

**Response Format (Success):**
```json
{
  "success": true,
  "result": { "count": N }
}
```

**Response Format (Error):**
```json
{
  "success": false,
  "error": "Command failed: error message",
  "failedIndex": N,
  "failedCommand": {...},
  "successCount": N
}
```

**RT-Safety:**
- Message thread only (same as all CommandAPI operations)
- No audio thread access
- Single transaction for entire batch (one undo action)

## Protocol v1: Zenith ↔ ai-bridge-server

### Request (Zenith → Server)

**Endpoint:** `POST http://localhost:8765/wingman`

**Headers:**
- `Content-Type: application/json`

**Body:**
```json
{
  "type": "wingman_nl_request",
  "requestId": "uuid-1234-5678-...",
  "text": "make a 4 bar MIDI drum loop and sidechain the bass",
  "sessionGraph": {
    "transport": { /* ... */ },
    "tracks": [ /* ... */ ]
  },
  "source": "zenith-core"
}
```

**Fields:**
- `type` - Always `"wingman_nl_request"`
- `requestId` - UUID generated by Zenith (for matching responses)
- `text` - User's natural language input
- `sessionGraph` - Full output from `SessionGraph::generateGraph()`
- `source` - Source identifier (default: `"zenith-core"`)

### Response (Server → Zenith)

**Success Response:**
```json
{
  "type": "wingman_nl_response",
  "requestId": "uuid-1234-5678-...",
  "status": "ok",
  "thought": "I'll create a MIDI track for drums and add a 4-bar clip starting at the current playhead position.",
  "commands": [
    {
      "command": "create_track",
      "params": { "type": "midi", "name": "Drums" }
    },
    {
      "command": "create_clip",
      "params": {
        "trackId": "track_0",
        "type": "midi",
        "start": 0,
        "length": 176400,
        "name": "Drum Loop"
      }
    }
  ]
}
```

**Error Response:**
```json
{
  "type": "wingman_nl_response",
  "requestId": "uuid-1234-5678-...",
  "status": "error",
  "error": "Model failed to generate commands: timeout"
}
```

**Fields:**
- `type` - Always `"wingman_nl_response"`
- `requestId` - Matches request UUID
- `status` - `"ok"` | `"error"`
- `thought` - AI's explanation of the plan (optional, shown to user)
- `commands` - Array of command objects `{command, params}`
- `error` - Error message if `status == "error"`

## Architecture Decisions

### 1. HTTP POST vs WebSocket

**Decision:** Use HTTP POST for v1 protocol

**Reason:**
- Simpler implementation (JUCE URL::createInputStream)
- Request/response model fits AI workflow (not streaming)
- No persistent connection management needed
- WebSocket adds complexity without clear benefit for this use case

**Tradeoff:**
- Slightly higher latency per request
- No server-initiated pushes (acceptable for v1)

**Future:** Could add WebSocket for streaming AI responses or multi-turn conversations

### 2. Yes/No Confirmation Workflow

**Decision:** Require explicit user confirmation before executing AI batches

**Reason:**
- Safety: AI could hallucinate destructive commands
- Transparency: User sees exactly what will be executed
- Education: Users learn command structure by example
- Trust: Gradual AI adoption without fear of mistakes

**Tradeoff:**
- Extra step slows workflow
- Breaks "magic" feeling of instant AI execution

**Future:** Could add "auto-execute" mode for trusted commands or trusted users

### 3. Single Undo Transaction

**Decision:** All AI batch commands execute in one undo transaction

**Reason:**
- User intent: "Do this task" = single conceptual action
- Undo simplicity: One Ctrl+Z reverts entire AI batch
- Matches user mental model of AI interaction

**Tradeoff:**
- If batch fails midway, successful commands are not auto-rolled back
- User must manually undo successful portion

**Future:** Could add automatic rollback on error (more complex)

### 4. Message-Thread Only

**Decision:** All AI operations execute on message thread, never audio thread

**Reason:**
- RT-safety: Network I/O must never block audio
- Consistency: Matches all CommandAPI behaviour
- Simplicity: No lock-free programming complexity

**Tradeoff:**
- Commands execute slightly slower (not RT-instant)
- Acceptable: AI workflow is inherently async (seconds)

### 5. Background Thread for Network I/O

**Decision:** AIBridgeClient runs network requests on background thread

**Reason:**
- Non-blocking: UI remains responsive during AI requests
- RT-safe: Audio thread never touched
- Async model: Matches AI latency (1-10 seconds typical)

**Implementation:**
- Inherits from `juce::Thread`
- Request queue with `CriticalSection`
- Response queue with `CriticalSection`
- `ChangeBroadcaster` notification on message thread

## Known Limitations

### 1. No Server Auto-Restart

**Limitation:** If ai-bridge-server crashes/stops, AIBridgeClient does not auto-reconnect

**Workaround:** Restart server manually, then retry request

**Future:** Add connection pooling, retry logic, or WebSocket auto-reconnect

### 2. No Partial Rollback

**Limitation:** If batch fails midway, successfully executed commands remain

**Impact:** User must manually undo successful commands

**Example:**
- Batch: `[create_track, invalid_cmd, create_clip]`
- Result: Track created, error at command #2, clip not created
- Undo once: Removes track (but leaves project in interim state during execution)

**Future:** Implement atomic batch execution with auto-rollback on error

### 3. Single AI Request at a Time

**Limitation:** System processes one AI request at a time (serial, not parallel)

**Impact:** If AI is slow (10s), user must wait before next request

**Future:** Support concurrent AI requests with request queue UI

### 4. No Streaming AI Responses

**Limitation:** AI must generate full command list before responding

**Impact:** No partial results, no "thinking..." indicator beyond static message

**Future:** WebSocket streaming for progressive command generation

### 5. No AI Model in zenith-core

**Limitation:** zenith-core does not include AI model - requires external server

**Impact:** Users must run ai-bridge-server separately

**Future:** Optionally bundle local model (e.g., llama.cpp) for offline use

### 6. No Command History for AI

**Limitation:** AI does not see previous requests or learn from user corrections

**Impact:** Each request is stateless, no conversational context

**Future:** Send conversation history in `sessionGraph` for multi-turn dialogue

### 7. No Undo for Cancelled Batches

**Limitation:** Typing `no` does not create undo entry (correct, but worth noting)

**Impact:** Cannot "redo" a cancelled AI batch

**Behaviour:** Intentional - cancellation discards commands permanently

### 8. No Per-Command Undo in Batch

**Limitation:** Entire batch is one undo transaction (all-or-nothing)

**Impact:** Cannot undo individual commands within a batch

**Design:** Intentional - matches user mental model of "AI action"

**Future:** Could add granular undo option in settings

### 9. Server URL Hardcoded

**Limitation:** `http://localhost:8765` is default, configurable only via code

**Impact:** Users cannot easily point to remote AI server

**Future:** Add settings UI for server URL configuration

### 10. No Timeout Indication

**Limitation:** If AI server is slow (>30s), user sees "(Waiting...)" indefinitely

**Impact:** No progress bar or timeout warning

**Future:** Add timeout with configurable duration, show elapsed time

## RT-Safety Verification

✅ **All AI operations are RT-safe:**

**AIBridgeClient:**
- Network I/O on background thread (never audio thread)
- Response queue with `CriticalSection` (message thread only)
- No real-time audio interaction

**WingmanPanel:**
- All UI interactions on message thread
- No audio thread access
- ChangeListener callbacks on message thread

**CommandAPI::executeBatch():**
- Executes on message thread (same as all CommandAPI methods)
- No audio thread mutations
- ValueTree + UndoManager are message-thread only

**No RT-Unsafe Operations:**
- ❌ No malloc/free in audio callback
- ❌ No locks held across audio buffer
- ❌ No network I/O in audio thread
- ❌ No UI updates in audio thread
